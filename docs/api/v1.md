## 1. Gemeinsamkeiten

### 1.1 Base URL

```
https://<gateway-host>/v1
```

`<gateway-host>` ist im PSM-Stack typischerweise `broker-gateway:4000` (intern) oder `broker-gateway.internal` über Reverse-Proxy.

### 1.2 Versionierung

- **Pfad-basiert.** `/v1/...` bleibt rückwärtskompatibel, solange die Major-Version unterstützt wird.
- **Additive Felder erlaubt.** Neue Felder in Responses sind keine Breaking-Change.
- **Semantische Änderungen** (Default-Werte, Error-Codes, Retry-Logik) erfordern eine neue Major-Version.
- Bei Deprecation einer Major-Version setzt der Service den Header `Deprecation: true` und `Sunset: <RFC7231-Datum>`.

### 1.3 Authentifizierung

Alle Endpoints (außer `/v1/auth/token` und `/v1/health`) verlangen einen API-Token im Header:

```
Authorization: Bearer <token>
```

Tokens sind opake Strings, ausgegeben über `/v1/auth/token`. Sie tragen Scope-Claims, die der Server bei jedem Request prüft. Fehlt ein erforderlicher Scope, antwortet der Server mit `403 Forbidden` und Body:

```json
{
  "error": {
    "code": "missing_scope",
    "message": "Required scope: orders:write",
    "required_scope": "orders:write"
  }
}
```

### 1.4 Scopes

Single Source of Truth ist `src/broker_gateway/auth/models.py`.

| Scope | Berechtigt zu |
|---|---|
| `instruments:read` | Symbol-Lookup, conid-Lookup |
| `quotes:read` | Snapshots + Streams |
| `portfolio:read` | Portfolio + Positions + Ledger + Trade-Historie |
| `orders:read` | Order-Status abfragen, Orders auflisten |
| `orders:write` | Orders platzieren / canceln |
| `events:read` | Events-Stream (Execution-Reports etc.) |
| `historical:read` | Historische Bars (`/v1/instruments/{conid}/historical/*`); seit v2.2.0 |
| `fundamentals:read` | Reuters-Fundamentals (`/v1/instruments/{conid}/fundamentals`); seit v2.2.0 |
| `admin:*` | Token-Verwaltung, Service-Internals; passt automatisch alle Scope-Checks |

Granulierung wird eingefuehrt, wenn ein Consumer sie tatsaechlich braucht — `historical:read` und `fundamentals:read` wurden in v2.2.0 separat aufgenommen, weil IBKR fuer historische Bars (Marktdaten-Pacing) und Reuters-Fundamentals (separates Abo) unterschiedliche Berechtigungen erwartet.

### 1.5 Idempotency

Schreib-Endpoints (`POST /v1/orders`, `DELETE /v1/orders/{id}`) verlangen einen Header:

```
Idempotency-Key: <client-generated UUID>
```

Server speichert `key → response` für 24 h. Wiederholte Requests mit demselben Key liefern die ursprüngliche Response — kein erneuter Broker-Call.

### 1.6 Error-Modell (final ab v1.5.0)

Alle Fehlerantworten der v1-API folgen demselben Envelope-Schema:

```json
{
  "error": {
    "code": "missing_scope",
    "message": "Token besitzt nicht den erforderlichen Scope 'orders:write'",
    "request_id": "a4e9...",
    "retry_after_s": 30,
    "extra": {
      "required_scope": "orders:write"
    }
  }
}
```

Pflicht-Felder: `code` und `message`. Optional: `request_id`,
`retry_after_s` und `extra`. Felder mit `null`-Wert werden vom Server
**weggelassen** statt mit `null` ausgeliefert. `extra` ist endpunkt-
spezifisch und niemals Teil des Vertrag-Stable-API — Consumer dürfen
sich nicht darauf verlassen.

#### Code-Tabelle (Single Source of Truth: `src/broker_gateway/api/v1/errors.py::KNOWN_ERROR_CODES`)

| Status | `code` | Wann | `extra` |
|--------|--------|------|---------|
| 400 | `invalid_input` | Pflicht-Header / Pfad-Parameter fehlt oder ist syntaktisch falsch (z.B. `Idempotency-Key` fehlt, `account_id` leer). | optional `errors`-Liste mit Pydantic-Detail |
| 401 | `missing_token` | `Authorization`-Header fehlt komplett. | — |
| 401 | `invalid_token` | Token unbekannt, abgelaufen oder Format `Bearer ...` falsch. | — |
| 403 | `missing_scope` | Token vorhanden aber Scope reicht nicht. | `{required_scope: "orders:write"}` |
| 404 | `not_found` | Ressource existiert nicht (Token, Order, conid). | — |
| 405 | `method_not_allowed` | Nicht-erlaubte HTTP-Methode auf bekanntem Pfad. | — |
| 409 | `conflict` | Generischer Konflikt (z.B. Token bereits revoked). | — |
| 409 | `idempotency_replay_mismatch` | Identischer `Idempotency-Key` mit anderem Body. | `{first_seen_at: ISO-8601}` |
| 415 | `unsupported_media` | `Content-Type` nicht `application/json`. | — |
| 422 | `invalid_input` | Request semantisch ungueltig (Pydantic-Validation, fachliche Pruefung). | optional `errors`-Liste |
| 429 | `cp_pacing_violation` | CP-Gateway hat 429 geliefert (IBKR-Pacing-Limit). Server retried bereits intern; wenn 429 nach aussen kommt, ist das ein dauerhafter Backoff. | — |
| 502 | `cp_upstream_error` | CP-Gateway hat einen unerwarteten 5xx oder Schema-Fehler geliefert, der nicht in eine spezifische `auth_lost`/`pacing`-Kategorie passt. | optional `{upstream_status, upstream_code}` |
| 503 | `auth_lost` | CP-Gateway-Session ist verloren oder gar nicht erreichbar (`AUTH_LOST` / `CP_DOWN`). Browser-2FA-Re-Login noetig. **Immer mit `Retry-After`-Header und `retry_after_s` im Body.** | `{auth_status: "auth_lost"}` |
| 504 | `cp_timeout` | CP-Gateway-Call lief in den Service-Timeout. | — |
| 500 | `internal_error` | Unbekannter Server-Bug. Sollte nie regelmaessig auftauchen. | — |

#### Verhaltens-Regeln

1. **`Retry-After`-Header und `retry_after_s` sind synchron.** Wenn der Server beides setzt, sind sie identisch. Consumer dürfen entweder den Header oder das Body-Feld lesen.
2. **`request_id` ist die Korrelations-ID** der `ObservabilityMiddleware`. Sie taucht in den strukturierten Server-Logs auf — bei Support-Anfragen mitsenden.
3. **CP-Gateway-Bodies werden NIE 1:1 durchgereicht.** Wenn IBKR z.B. einen HTML-Error-Body liefert, übersetzt der Service ihn in `cp_upstream_error` mit gefilterten Feldern in `extra`.
4. **`extra` ist niemals Pflicht.** Consumer dürfen es ignorieren. Server darf neue `extra`-Felder ohne Versions-Bump hinzufügen — aber bestehende nicht silent umbenennen.
5. **IBKR liefert haeufig HTTP 500/503 fuer Anwendungs-Fehler** (Live-Beobachtung in AP-02 #05: `qty=0` → 500, unknown order → 503, unknown conid → 500). Der Service-Code mappt diese auf semantische `code`-Werte basierend auf dem Body-Inhalt — der Status-Code allein ist nicht aussagekraeftig.

### 1.7 Pagination

Listen-Endpoints unterstützen Cursor-Pagination:

- Request: `?limit=100&cursor=<opaque>`
- Response: `{ "items": [...], "next_cursor": "..." | null }`

### 1.8 Datum / Zeit

Alle Zeitstempel als ISO-8601 mit Timezone (UTC bevorzugt):

```
2026-04-24T17:30:00Z
```

### 1.9 Geld-Beträge

Alle Geld-Felder als Objekt:

```json
{ "value": "274.06", "currency": "USD" }
```

`value` ist String (verhindert Float-Rounding). Currency ist ISO-4217.

## 2. Authentifizierung

Tokens sind **opake Strings** (kein JWT), serverseitig generiert über `secrets.token_urlsafe(32)` und im Token-Store persistiert. Backend-Auswahl per ENV:

- ohne `BG_TOKEN_FILE` → `InMemoryTokenStore` (Default; State geht beim Neustart verloren — das ist Absicht, der Service ist transient).
- mit `BG_TOKEN_FILE=/path/to/tokens.json` → `FileTokenStore` (atomarer Write via temp-file + rename).

Beim Start liest die App optional `BG_BOOTSTRAP_ADMIN_TOKEN`; ist die Variable gesetzt und das Token noch nicht im Store, wird es als Token mit `caller_id=bootstrap-admin` und Scopes `[admin:*]` registriert. So kann initial mindestens ein Admin-Aufruf erfolgen, ohne dass weitere Tokens im Repo oder Compose-File liegen.

### 2.1 Token erstellen

```
POST /v1/auth/token
Authorization: Bearer <admin-token>          ← muss admin:* tragen
Content-Type: application/json

{
  "caller_id": "psm",
  "scopes": ["quotes:read", "portfolio:read", "instruments:read"],
  "expires_at": "2027-04-24T17:30:00Z"        ← optional
}
```

Response `201 Created`:

```json
{
  "value": "RANDOM_OPAQUE_TOKEN_VALUE",
  "caller_id": "psm",
  "scopes": ["quotes:read", "portfolio:read", "instruments:read"],
  "created_at": "2026-04-24T17:30:00.123Z",
  "expires_at": "2027-04-24T17:30:00Z"
}
```

Fehlerfälle:

| Status | Bedingung |
|---|---|
| `401 Unauthorized` | kein/ungültiges Bearer-Token |
| `403 Forbidden` | aufrufendes Token hat nicht `admin:*` |
| `422 Unprocessable Entity` | unbekannte Scope-Namen oder leere `caller_id` |

### 2.2 Token revoken

```
DELETE /v1/auth/token
Authorization: Bearer <token>
DELETE /v1/auth/token?value=<other-token>     ← admin:* nötig
```

Ohne Query-Parameter `value` revoket der Aufruf das eigene Bearer-Token (Self-Revoke, kein admin:* nötig). Wird ein fremdes Token-Value angegeben, ist `admin:*` Pflicht.

Response `204 No Content`.

Fehlerfälle:

| Status | Bedingung |
|---|---|
| `401 Unauthorized` | kein/ungültiges Bearer-Token |
| `403 Forbidden` | fremdes Token ohne `admin:*` |
| `404 Not Found` | Token-Value existiert nicht (mehr) |

## 3. Health

### 3.1 Public Health

```
GET /v1/health
```

Kein Auth nötig. Response 200:

```json
{
  "status": "ok",
  "version": "0.4.0"
}
```

### 3.2 Internal Health (Detail)

```
GET /v1/internal/health
Authorization: Bearer <admin-token>
```

Erfordert Scope `admin:*`. Liefert immer `200`, auch wenn die IBKR-Session verloren ist - das Endpunkt-Ziel ist genau, das zu zeigen.

Response 200 (Stand v1.34.1, gegen Live verifiziert):

```json
{
  "auth_status": "ok",
  "auth_status_consumer": "ok",
  "cp_reachable": true,
  "last_tickle_at": "2026-05-04T08:39:11.968418Z",
  "last_reauth_at": null,
  "last_sso_validate_at": "2026-05-04T08:39:11.902646Z",
  "last_login_at": "2026-05-04T07:38:11.968426Z",
  "session_age_s": 60.92,
  "consecutive_reauth_failures": 0,
  "accounts_initialized": true,
  "iserver_bridge_ok": true,
  "last_bridge_probe_at": "2026-05-04T08:39:12.123456Z",
  "consecutive_bridge_failures": 0
}
```

| Feld | Bedeutung |
|---|---|
| `auth_status` | Roher Lifecycle-Status. **CP-Backend** (`BG_BACKEND=cp`): `ok` / `reauth_pending` / `auth_lost` / `cp_down`. **TWS-Backend** (`BG_BACKEND=tws`): `ok` / `session_lost` / `tws_down`. Single Source of Truth: `broker_gateway.auth_status.AuthStatus` (sechs Werte gesamt, ab v1.34.0). Wird für Operations-Diagnose nicht-breaking weiter im Klartext geliefert. |
| `auth_status_consumer` | Stabiler Konsumenten-View, abgeleitet aus `auth_status` über `to_consumer_status`: `ok` / `down` (Backend nicht erreichbar) / `lost` (Backend erreichbar, Session verloren). Backend-unabhängig — Konsumenten-Code parsen ausschließlich dieses Feld. Ab v1.34.0. |
| `cp_reachable` | Letzter HTTP-Call zum CP-Gateway hat geantwortet. Im TWS-Pfad spiegelt das Feld `ib.isConnected()` (Adapter-Mapping). |
| `last_tickle_at` | CP-Backend: UTC-Timestamp des letzten Tickle-Calls. TWS-Backend: UTC-Timestamp des letzten Heartbeats (Adapter-Mapping aus `last_heartbeat_at`). `null` vor dem ersten Aufruf. |
| `last_reauth_at` | CP-Backend: UTC-Timestamp des letzten Reauth-Versuchs. TWS-Backend: immer `null` (keine Reauth-Mechanik — IB Gateway + IBC übernehmen Daily-Restart und Saturday-Reset selbständig). |
| `last_sso_validate_at` | CP-Backend: UTC-Timestamp des letzten erfolgreichen `/sso/validate`-Calls. TWS-Backend: immer `null`. |
| `last_login_at` | UTC-Timestamp des letzten Übergangs auf `auth_status=ok`. |
| `session_age_s` | Sekunden seit `last_login_at`. |
| `consecutive_reauth_failures` | CP-Backend: aufeinanderfolgende fehlgeschlagene Reauth-Versuche; reset auf `0` bei `ok`. TWS-Backend: immer `0`. |
| `accounts_initialized` | CP-Backend: `true`, sobald `/iserver/accounts` einmal erfolgreich war (initialer Account-Bootstrap). TWS-Backend: spiegelt `is_ready` (Adapter-Mapping aus `ib.client.isReady()`). |
| `iserver_bridge_ok` | CP-Backend: Letztes Resultat des iserver-Bridge-Probes via `GET /iserver/auth/status`. TWS-Backend: immer `null` — die TWS-API hat keine Bridge-Konzeption. (ab v1.26.0) |
| `last_bridge_probe_at` | CP-Backend: UTC-Timestamp des letzten Bridge-Probes. TWS-Backend: immer `null`. (ab v1.26.0) |
| `consecutive_bridge_failures` | CP-Backend: aufeinanderfolgende Bridge-Drift-Befunde. TWS-Backend: immer `0`. (ab v1.26.0) |

#### Auth-Lifecycle (CP- und TWS-Backend)

Der Service hält genau **eine** IBKR-Trading-Session offen. Seit v1.34.0 (Karte 33cb35b1) gibt es zwei Backend-Pfade, gewählt über `BG_BACKEND` (Default `cp`):

**CP-Backend (`BG_BACKEND=cp`, Default):** Hintergrund-Tickle-Job gegen das interne CP Gateway.

- Intervall: alle `BG_CP_TICKLE_INTERVAL_S` Sekunden (Default `60`).
- Bei `authenticated=false` aus `tickle`/`auth_status` wechselt der Status auf `reauth_pending`. Es werden bis zu drei `reauthenticate`-Versuche mit exponential backoff (Basis `2 s`) gemacht. Bleibt der Versuch erfolglos, fällt der Status auf `auth_lost`.
- HTTP-Fehler beim Aufruf des CP-Gateways setzen den Status auf `cp_down`.
- Erfolgreiches Tickle nach Verlust setzt `auth_status` direkt zurück auf `ok`, ohne dass externe Endpunkte etwas tun müssen.

**TWS-Backend (`BG_BACKEND=tws`):** Heartbeat-Loop gegen IB Gateway + IBC via `ib_async`-Socket-Verbindung.

- Intervall: alle `BG_TWS_HEARTBEAT_SEC` Sekunden (Default `60`).
- State-Maschine pro Tick: Wenn `ib.isConnected()` falsch ist, Connect-Versuch (max. `BG_TWS_MAX_CONNECT_FAILURES` in Folge, Default `3`, danach `tws_down`). Wenn verbunden, Health-Check via `ib.client.isReady()`. Ergebnis: `ok` oder `session_lost`.
- **Keine Reauth-Mechanik:** IB Gateway + IBC übernehmen Daily-Restart und Saturday-Reset selbständig. Nach einem TWS-Restart erkennt der Heartbeat den Verlust und reconnected automatisch.
- **Single-Owner-Constraint** bleibt: jede TWS-API-Verbindung belegt eine `clientId`; broker-gateway hält die ID dauerhaft.

**Konsumenten-Sicht:** Beide Backends rendern dasselbe `/v1/internal/health`-Schema. Konsumenten-Code parsen das stabile `auth_status_consumer`-Feld (`ok | down | lost`); das rohe `auth_status`-Feld bleibt für Operations-Diagnose erhalten. Der 503-Guard der Business-Endpunkte (siehe nächster Block) reagiert backend-unabhängig auf `is_session_unavailable(status)` aus `broker_gateway.auth_status`.

#### iserver-Bridge-Probe (ab v1.26.0)

Zusätzlich zum Tickle-Loop läuft ein separater Health-Pfad, der die iserver-Backend-Bridge zu IBKR überwacht. Hintergrund: ein gefallener iserver-Bridge lässt SSO-Tickle und `/sso/validate` weiterhin grün antworten, bricht aber jeden iserver-Call mit `400 Bad Request: no bridge` (Live-Befund 2026-05-03 nach 21h Standzeit). Ohne den Probe blieb das vom Service unbemerkt — `internal/health` meldete `auth_status=ok`, während alle Business-Endpunkte 502 lieferten.

- **Intervall:** alle `BG_CP_BRIDGE_PROBE_INTERVAL_S` Sekunden (Default `120`); läuft im selben Hintergrund-Task wie der Tickle-Job, also typischerweise jeden zweiten Tickle-Zyklus.
- **Healthy:** `GET /iserver/auth/status` liefert das Trio `authenticated=true`, `established=true`, `connected=true` → `iserver_bridge_ok=true`, Failure-Counter zurück auf `0`.
- **Drift erkannt:** mindestens eines der drei Felder ist `false`. Der Lifecycle setzt `iserver_bridge_ok=false`, triggert einen einmaligen `POST /iserver/reauthenticate` und wartet `15 s` (`bridge_reauth_warmup_s`). Erfolgs-Recheck via `auth_status` — bei wiederhergestelltem Trio springt `iserver_bridge_ok` zurück auf `true`.
- **Persistenter Drift:** nach drei aufeinanderfolgenden fehlgeschlagenen Probe-und-Recovery-Versuchen eskaliert der Lifecycle pragmatisch auf `auth_status=auth_lost`. Damit greift das bestehende 503-Verhalten der Business-Endpunkte (Section 3.2 unten); keine neue `auth_status`-Variante eingeführt.
- **Skip-Bedingungen:** Bei `auth_status in {auth_lost, cp_down}` wird der Bridge-Probe übersprungen — der Tickle-Pfad kümmert sich um die Recovery, und ein zusätzlicher Probe würde den Failure-Counter unnötig erhöhen.

#### 503-Verhalten der Business-Endpunkte

Alle nachfolgenden Endpunkte (Quotes, Portfolio, Orders, Trades, Events) hängen die Dependency `require_session_ok` ein. Sie ruft `is_session_unavailable(auth_status)` aus `broker_gateway.auth_status` — ab v1.34.0 die zentrale Quelle für die 503-Auswertung. Aktuell trifft das auf `auth_lost`, `cp_down`, `session_lost` und `tws_down` zu (`reauth_pending` ist erlaubt). Antwort:

```
HTTP/1.1 503 Service Unavailable
Retry-After: 30
Content-Type: application/json

{"detail": "IBKR-Session nicht verfuegbar (status=auth_lost)"}
```

Der `status`-Suffix im Body trägt den rohen Backend-Status (z.B. `auth_lost` im CP-Pfad, `session_lost` im TWS-Pfad). `/v1/health` und `/v1/internal/health` sind von dieser Sperre **ausgenommen**, damit Operations auch bei verlorener Session noch arbeiten können.

| `BG_CP_BASE_URL` | `http://cpgateway:5000/v1/api` | Base-URL des internen CP Gateways inkl. `/v1/api`-Prefix (CP-Backend). |

## 4. Instruments

Alle Endpunkte erfordern Scope `instruments:read` und einen aktiven Auth-Lifecycle (`auth_status=ok`). Bei `auth_status in {auth_lost, cp_down}` antworten sie mit `503 Service Unavailable` + `Retry-After: 30` (Section 3.2).

Symbol-Lookups werden in einem **TTL-Cache (Default 7 Tage)** gehalten. conid-Mappings ändern sich praktisch nie, und CP-Gateway-Calls sind teuer und ratelimitiert (Section 10).

### 4.1 Search

Zwei alternative Lookup-Modi: per Ticker-Symbol oder per ISIN. Genau einer der beiden Parameter (`symbol` oder `isin`) muss gesetzt sein; sonst antwortet der Adapter mit `422 Unprocessable Entity`.

```
GET /v1/instruments/search?symbol=AAPL[&exchange=NASDAQ]
GET /v1/instruments/search?isin=DE0007164600[&mic=XETR]
Authorization: Bearer <token (instruments:read)>
```

| Parameter | Pfad | Bedeutung |
|---|---|---|
| `symbol` | symbol-Pfad | Ticker, z.B. `AAPL`. Mutually exclusive zu `isin`. |
| `exchange` | symbol-Pfad | optional; IBKR-Routing-Kuerzel (z.B. `NASDAQ`). Nur in Kombination mit `symbol`. |
| `isin` | ISIN-Pfad | ISO 6166 (12 Zeichen: 2 Land + 9 alphanumerisch + 1 Pruefziffer). Ungueltiges Format -> `422`. |
| `mic` | ISIN-Pfad | optional; ISO 10383 MIC (z.B. `XETR`, `XNYS`) zur Cross-Listing-Disambiguation. Nur in Kombination mit `isin`. |

Response 200 (v1.27.0 - Liste statt Paginierungs-Wrapper, da Suchen wenige Treffer liefern):

```json
[
  {
    "conid": 265598,
    "symbol": "AAPL",
    "company_name": "APPLE INC",
    "currency": "USD",
    "sec_type": "STK",
    "isin": null
  }
]
```

| Feld | Bedeutung |
|---|---|
| `conid` | IBKR-interne Instrument-ID (int) |
| `symbol` | Ticker, immer upper-case |
| `company_name` | Klartext-Name (kann `null` sein) |
| `currency` | ISO-4217-Code (kann `null` sein) |
| `sec_type` | `STK` / `OPT` / `FUT` / ... (kann `null` sein) |
| `isin` | ISO-6166-ISIN. Symbol-Pfad: `null` (CP-Gateway liefert keine ISIN). ISIN-Pfad: Echo des Query-Werts. Ergaenzt in v1.27.0. |

Unbekannte Symbole bzw. unbekannte ISINs liefern in der Regel `200` mit leerem Array. Wenn das CP-Gateway ein unerwartetes Schema zurueckgibt (kein Listen-Response, sondern ein abweichendes Objekt — empirisch beobachtet bei unbekannten Symbolen wie `XYZINVALID9999` gegen das Paper-Gateway), liefert der Adapter `502 cp_upstream_error` mit Error-Envelope. Beide Antworten sind kontraktlich akzeptabel; der Consumer behandelt 4xx/5xx mit dem Standard-Backoff (Section 1.6).

#### ISIN-Pfad und Cross-Listing

Eine ISIN ist marktneutral (ISO 6166); fuer Cross-Listings (z.B. SAP an Xetra/IBIS und als ADR an NYSE) liefert IBKR mehrere Eintraege pro ISIN. Der Adapter gibt die CP-Reihenfolge unveraendert weiter — IBKR sortiert intern nach Liquiditaets-Heuristik (Primary Exchange in der Regel zuerst). Wer deterministisch ein bestimmtes Listing braucht, schickt zusaetzlich `mic=<MIC>` (ISO 10383). Beispiele:

- `?isin=DE0007164600` → SAP-Cross-Listings (NYSE-ADR + IBIS)
- `?isin=DE0007164600&mic=XETR` → nur das Heimat-Listing (IBIS)
- `?isin=DE0007164600&mic=XNYS` → nur die NYSE-ADR

Die `?isin=` Variante mappt intern auf den IBKR-Endpunkt `/iserver/secdef/search?symbol=<ISIN>&name=true&secType=STK`. Andere `secType`-Werte (Optionen/Futures auf eine ISIN) sind ein Folge-Karten-Thema.

#### Contract-Trading-Hours — Format und Semantik (seit v1.37.0)

`trading_hours` und `liquid_hours` reichen die IBKR-`ContractDetails`-Felder
**roh und verlustfrei** durch (kein serverseitiges Parsing). Format:

- Tagessegmente sind durch `;` getrennt, eines oder mehrere pro Handelstag.
- Offener Tag: `YYYYMMDD:HHMM-YYYYMMDD:HHMM` (Start- und End-Zeitstempel je
  mit Datum — eine Session kann über Mitternacht laufen, daher das
  wiederholte Datum). Mehrere Segmente pro Tag sind möglich.
- Geschlossener Tag (Feiertag oder Wochenende): `YYYYMMDD:CLOSED`.
- Alle Uhrzeiten gelten in der Zone `time_zone_id`.

Daraus sind alle von der Karte geforderten Sichten **zeitzonen-behaftet
ableitbar**:

| Sicht | Ableitung |
|---|---|
| **RTH** (Regular Trading Hours) | `liquid_hours` |
| **ETH** (Extended/alle Sessions) | `trading_hours` (umfasst Pre-/Post-Market) |
| **Feiertag** | Tag erscheint als `…:CLOSED` (bzw. fehlt) |
| **Halbtag** | verkürzte Schlusszeit in `liquid_hours` (z.B. `1300` statt `1600`) |
| **Zeitzone** | `time_zone_id` (IANA-/IBKR-Zone) für alle Zeitstempel |

**Konsumenten-Vertrag (trading_robot, Karte 345fe163 / ADR-0018):** Der
trading_robot hebt seine `TradingWindowRule` kalender-gestützt aus
`liquid_hours` (RTH-Fenster) und `time_zone_id` (zeitzonen-korrekte
Interpretation); Feiertage/Halbtage werden aus den `CLOSED`-Markierungen
bzw. verkürzten Schlusszeiten erkannt, `trading_hours` deckt zusätzlich
Pre-/Post-Market ab. Wer statt der rohen Strings eine bereits
strukturierte Session-Sicht braucht, folgt `calendar_url` →
[`/v1/exchanges/{id}/calendar`](#) (Static-Mapping-Kalender, 14 Tage). Die
Felder sind additiv; ein Consumer, der sie ignoriert, bleibt
vertragskonform.

### 5.1 Snapshot

```
GET /v1/quotes/snapshot?conids=265598,272093[&fields=last,bid,ask,availability]
Authorization: Bearer <token (quotes:read)>
```

`fields` ist eine Komma-Liste aus normalisierten Namen. Mapping zu IBKR-Field-IDs ist intern (Single Source of Truth: `broker_gateway.cp.quotes.FIELD_ALIASES`).

| Alias | IBKR-Code | Bedeutung |
|---|---|---|
| `last` | `31` | Letzter gehandelter Preis |
| `bid` | `84` | Aktuelles Bid |
| `ask` | `86` | Aktuelles Ask |

```json
[
  {
    "conid": 265598,
    "last": "150.50",
    "bid": "150.45",
    "ask": "150.55",
    "volume": null,
    "change_pct": null,
    "high": null,
    "low": null,
    "availability": "delayed",
    "availability_raw": "DPB",
    "updated_at": "2026-04-25T11:30:14.481Z"
  }

```

| Feld | Bedeutung |
|---|---|
| `last`/`bid`/`ask`/... | als String, um Float-Rounding zu vermeiden; `null` falls IBKR den Wert (noch) nicht geliefert hat |
| `volume` | Tagesvolumen in Aktien als Integer-String (z.B. `"129338122"` für ~129 Mio Aktien). Quirk: IBKR-Field 7762 liefert den Wert × 10⁶ als rohen Integer; der Service dividiert intern und liefert die Aktien-Anzahl. Werte ausserhalb 0..10¹⁶ werden als IBKR-Drift erkannt und auf `null` gemappt (Warning im Log). Empirie 2026-05-03 (DUP799747-Frozen-Snapshot): NVDA 7762=129338122634379 → volume `"129338122"`. |
| `availability` | normalisiert auf `realtime` / `delayed` / `frozen` / `null` (Single Source of Truth: `broker_gateway.availability.map_availability`) |
| `availability_raw` | Originaler IBKR-6509-Code (z.B. `DPB`) - bleibt erhalten, falls Consumer ihn ausnahmsweise braucht |

#### First-Call-Prime (intern)

CP-Gateway-Quirk (Anhang 1.5): der erste Snapshot-Call für eine neue conid liefert leere Felder - das `marketdata/snapshot`-Endpunkt primt CP-intern erst die Subscription. Erst der zweite Call hat die echten Werte.

Der Service absorbiert das nach aussen: jeder `/v1/quotes/snapshot`-Aufruf macht intern **zwei** sequenzielle CP-Gateway-Calls (kurzer 300 ms-Delay dazwischen) und gibt nur das Second-Call-Ergebnis zurück. Consumer sieht immer Daten oder Error.

### 5.2 Stream (SSE)

```
GET /v1/quotes/stream?conids=265598,272093[&fields=last,bid,ask]
Authorization: Bearer <token (quotes:read)>
Accept: text/event-stream
[Last-Event-ID: <last-seen-event-id>]
```

`fields` und Default-Verhalten identisch zu Section 5.1 (Snapshot). `availability` wird intern immer angefordert.

Response `200 OK` mit `Content-Type: text/event-stream` und Frames im SSE-Format:

```
id: 0
event: quote
data: {"conid":265598,"last":"150.50","bid":"150.45","ask":"150.55","availability":"delayed","availability_raw":"DPB","updated_at":"2026-04-25T11:30:14.481Z"}

id: 1
event: quote
data: {"conid":272093,"last":"320.10","bid":"320.05","ask":"320.15","availability":"delayed","availability_raw":"DPB","updated_at":"2026-04-25T11:30:14.498Z"}
```

`event` ist immer `quote`, `data` enthält dasselbe Schema wie ein Snapshot-Eintrag. `id` ist eine vom Server vergebene, **monoton steigende** Event-ID (Single Source of Truth: `broker_gateway.streams.manager._ConidSubscription._next_event_id`).

#### Subscription-Refcount + Fan-Out

Anders als das CP-Gateway, das Subscriptions session-global hält, bietet `broker-gateway` Refcount + Fan-Out:

- Pro `conid` läuft genau **eine** interne Subscription (Polling gegen `/iserver/marketdata/snapshot`, kein nativer CP-Stream-Endpunkt in v1).
- Mehrere parallele HTTP-Consumer auf denselben `conid` teilen sich diese eine Subscription. Jeder Consumer bekommt jede Quote-Aktualisierung.
- Disconnect eines Consumers (TCP-Close, Browser-Reload, Process-Exit) dekrementiert den Refcount. Bei `refcount=0` startet ein **5-Sekunden-Cool-Down**; verbindet binnen dieser Zeit ein neuer Consumer, wird der Cool-Down gecancelt und die Subscription bleibt warm. Andernfalls wird `/iserver/marketdata/{conid}/unsubscribe` gerufen.

#### Reconnect via Last-Event-ID

Sendet der Client beim Reconnect den `Last-Event-ID`-Header, liefert der Server zunächst alle gepufferten Events mit `id > Last-Event-ID` und schaltet dann auf den Live-Stream um. Buffergröße ist 200 Events pro `conid`. Wenn der Reconnect zu spät kommt, fehlen Events - Consumer sollte in dem Fall einen `/v1/quotes/snapshot` als Cold-Start ergänzen.

#### Limits + Fehlercodes

| Status | Bedingung |
|---|---|
| `429 Too Many Requests` mit `Retry-After: 30` | Manager hat das CP-Gateway-Limit von **250 parallel aktiven conids** erreicht |
| `503 Service Unavailable` mit `Retry-After: 30` | `auth_status in {auth_lost, cp_down}` (siehe Section 3.2) |
| `403 Forbidden` | Token hat nicht `quotes:read` |
| `401 Unauthorized` | Token fehlt / ungültig / abgelaufen |
| `422 Unprocessable Content` | leere/ungültige `conids` oder unbekannte `fields` |

#### Verhältnis Snapshot ↔ Stream

Beide Endpunkte nutzen dasselbe Field-Alias-Mapping und denselben Quote-Body. Wer einmalig Daten will, ruft Snapshot. Wer kontinuierlich Updates braucht, hängt sich an Stream. Mischbetrieb (Snapshot warm-start + Stream danach) wird vom Server gut vertragen, da Subscription-Refcount global ist.

## 6. Portfolio

Alle Endpunkte erfordern Scope `portfolio:read` und einen aktiven Auth-Lifecycle (`auth_status=ok`). Bei `auth_status in {auth_lost, cp_down}` antworten sie mit `503 Service Unavailable` + `Retry-After: 30` (Section 3.2).

Antworten werden in einem **TTL-Cache (Default 30 s, ENV `BG_PORTFOLIO_TTL_S`)** gehalten. Das Order-Subsystem (Section 7) ruft `PortfolioService.invalidate(account_id)` nach erfolgreichem Place/Cancel auf, damit nachfolgende Reads einen frischen Stand liefern.

Geldwerte folgen Section 1.9 (`{value, currency}` mit String-Value gegen Float-Drift). Single Source of Truth fuer die Normalisierung: `broker_gateway.money.normalize_money`.

### 6.1 Summary

## 7. Orders

### 7.0 Idempotency-Konvention

Schreiboperationen (`POST /v1/orders`, `DELETE /v1/orders/{order_id}`) verlangen den HTTP-Header `Idempotency-Key`. Konvention: vom Caller erzeugte UUID v4 oder andere kollisionsarme Token. Pflicht-Verhalten:

- **Fehlt** der Header: `400 Bad Request`, Body `{"detail": "Idempotency-Key-Header ist Pflicht"}`.
- **Erstaufruf** mit Key wird verarbeitet und das Ergebnis im Idempotency-Cache abgelegt (TTL Default 24 h, ENV `BG_IDEMPOTENCY_TTL_S`).
- **Replay** mit demselben Key liefert die gespeicherte Antwort, aber mit Status `200 OK` (statt 201 für Place). Der Body ist identisch zum Erstaufruf - der CP-Gateway wird nicht erneut getroffen.
- Der Schluessel wird pro HTTP-Methode gescoped, d.h. POST und DELETE koennen denselben Key tragen, ohne zu kollidieren.

| ENV | Default | Wirkung |
|---|---|---|
| `BG_IDEMPOTENCY_TTL_S` | `86400` | TTL in Sekunden fuer einen Idempotency-Eintrag |

### 7.1 Place (implementiert in v0.9.0)

```
POST /v1/orders
Authorization: Bearer <token (orders:write)>
Idempotency-Key: 7c3b2a8e-...
Content-Type: application/json

{
  "account_id": "U25235077",
  "conid": 265598,
  "side": "BUY",
  "quantity": "1",
  "order_type": "LMT",
  "limit_price": "270.00",
  "tif": "DAY"
}
```

`order_type` ist eines aus `LMT`, `MKT`, `STP`, `STP-LMT` — Werte ausserhalb dieser Menge werden mit `422 Unprocessable Content` abgelehnt. `quantity`, `limit_price`, `stop_price` sind Decimal-Strings (kein Float). Combinations:

| `order_type` | Pflichtfelder |
|---|---|
| `LMT` | `limit_price` |
| `MKT` | (keine) |
| `STP` | `stop_price` |
| `STP-LMT` | `limit_price` + `stop_price` |

Reply-Confirmation-Loop: Das CP-Gateway antwortet bei einer Place-Anfrage gelegentlich mit einer Liste von Warning-Confirmations (Schema `[{id, message: [...]}]`) statt direkt mit der Order. Der Service quittiert solche Warnings transparent per `POST /iserver/reply/{id}` mit `{"confirmed": true}` und liefert erst die finale Order. Die Warning-Texte werden an den Caller im Feld `warnings` durchgereicht.

Response 201 (Erstaufruf):

```json
{
  "order_id": "1000000",
  "account_id": "U25235077",
  "conid": 265598,
  "side": "BUY",
  "quantity": "1",
  "order_type": "LMT",
  "tif": "DAY",
  "status": "PendingSubmit",
  "limit_price": "270.00",
  "stop_price": null,
  "avg_fill_price": null,
  "commission": null,
  "filled_quantity": null,
  "submitted_at": null,
  "warnings": []
}
```

Response 200 bei Replay (gleicher Key): identischer Body.

Fehler:

| Status | Bedingung |
|---|---|
| 400 | `Idempotency-Key`-Header fehlt |
| 401/403 | kein Token / falscher Scope |
| 422 | `order_type` ungueltig oder Pflichtfeld fehlt |
| 503 | IBKR-Session nicht verfuegbar (`Retry-After: 30`) |

### 7.4 What-If (Preview) — implementiert in v2.3.0

Vor einer echten Order kann man eine Margin-/Risk-Preview holen. Der Endpoint **platziert nichts** — er ist eine reine Vorschau und daher mit dem Lese-Scope erreichbar.

```
POST /v1/orders/whatif
Authorization: Bearer <token (orders:read; orders:write wird ebenfalls akzeptiert)>
Content-Type: application/json

{
  "account_id": "U25235077",
  "conid": 265598,
  "side": "BUY",
  "quantity": "1",
  "order_type": "LMT",
  "limit_price": "270.00",
  "tif": "DAY"
}
```

Der Request-Body ist identisch zu `POST /v1/orders` (dasselbe `OrderRequest`-Schema und dieselben Typ-Validierungen). Es ist **kein** `Idempotency-Key` nötig.

Response 200 (`WhatIfPreview`):

```json
{
  "account_id": "U25235077",
  "conid": 265598,
  "estimated_amount":      { "value": "270.00", "currency": "USD" },
  "estimated_commission":  { "value": "1.00",   "currency": "USD" },
  "estimated_total":       { "value": "271.00", "currency": "USD" },
  "margin_impact": {
    "current_funds":      { "value": "179.54", "currency": "EUR" },
    "after_funds":        { "value": "91.00",  "currency": "EUR" },
    "init_margin_after":  { "value": "88.00",  "currency": "EUR" },
    "maint_margin_after": { "value": "80.00",  "currency": "EUR" }
  },
  "warnings": [
    {
      "code": "no_market_data_subscription",
      "raw_id": 21,
      "message": "You are trying to submit an order without having market data for this instrument."
    }
  ]
}
```

**Feld-Semantik (TWS-Backend, Quelle `ib_async.OrderState`):**

| Feld | Quelle / Bedeutung |
|---|---|
| `estimated_amount` | `quantity * limit_price` in Contract-Currency. `null` bei MKT/STP ohne Limit-Preis (kein Schätzpreis). |
| `estimated_commission` | Konservative Schätzung (`maxCommission`, sonst `commission`) in `commissionCurrency`. |
| `estimated_total` | `estimated_amount + estimated_commission`, nur bei identischer Currency; sonst `null`. |
| `margin_impact.current_funds` / `after_funds` | Equity-with-Loan vor/nach der Order, in Account-Base-Currency. |
| `margin_impact.init_margin_after` / `maint_margin_after` | Initial-/Maintenance-Margin nach der Order. |
| `warnings[]` | Pre-Trade-Warnungen. `raw_id` = IBKR-Warning-Code, sofern vorhanden; `code` semantisch abgeleitet (sonst `whatif_warning`). |

**Wichtige Einschränkungen:**

- **Alle Geldfelder sind optional.** Liefert das Backend einen Wert nicht (z.B. Margin-Felder ohne aktive Account-Subscription, oder keine Base-Currency ermittelbar), bleibt das Feld `null` statt geschätzt zu werden.
- **Backend-Abhängigkeit:** Die Vorschau läuft über das TWS-Backend (`ib_async.whatIfOrder`). Das Roll-Back-Profil `cp-legacy` liefert hier `503 whatif_not_supported_on_cp`, da das CP-Gateway nur vorformatierte Strings zurückgibt, die nicht verlustfrei auf dieses Schema mappen.
- **Write-fähige Session erforderlich:** IBKR behandelt `whatIfOrder` als Order-Validierung und lehnt ihn im **Read-Only-API-Modus** ab (`Warning 321: The API interface is currently in Read-Only mode`) — ohne einen `OrderState` zu liefern, was den Call hängen ließe. Der Service erkennt das proaktiv und antwortet im read-only-Modus sofort mit `503 whatif_requires_write_session`. whatif gehört damit funktional zum **Schreib-Workflow**: wie `POST /v1/orders` braucht es eine nicht-read-only Session. Der Token-Scope (`orders:read`) regelt nur die *Berechtigung*, nicht die Session-*Fähigkeit*. (Beide cma-pi-1-Stacks laufen heute `read_only=yes` — ein whatif-Aufruf liefert dort den dokumentierten 503; eine echte Vorschau erfordert einen Stack mit `READ_ONLY_API=no`.)
- **Hang-Schutz:** Der `whatIfOrderAsync`-Call ist zusätzlich mit einem 15s-`asyncio.wait_for`-Timeout abgesichert; bleibt ein OrderState in einer Write-Session aus, kommt `504 tws_whatif_timeout` statt eines blockierten Workers.

### 8.1 Trade-Historie (implementiert in v0.10.0)

```
GET /v1/trades?from=2026-04-01&to=2026-04-25&account_id=U25235077
Authorization: Bearer <token (portfolio:read)>
```

Query-Parameter:

| Parameter | Default | Wirkung |
|---|---|---|
| `from` | `today - 7d` | Startdatum (inklusive) |
| `to` | `today` | Enddatum (inklusive) |
| `account_id` | `null` | Optionaler Filter; Trades aus mehreren Accounts werden sonst zusammengefuegt |

- Maximaler Lookback: **30 Tage** (`from` darf nicht weiter als 30 Tage vor `today` liegen → 400).
- `to >= from`, sonst 400.
- Der Service uebersetzt das Window in den CP-Gateway-Parameter `days = today - from + 1` und filtert clientseitig nach `to`.

Response 200:

```json
{
  "items": [
    {
      "execution_id": "exec-000",
      "order_id": "ord-000",
      "account_id": "U25235077",
      "conid": 265598,

      "side": "BUY",
      "quantity": "1",
      "price":      { "value": "150.00", "currency": "USD" },
      "net_amount": { "value": "150.00", "currency": "USD" },
```

`currency_assumed: true` markiert einen Trade, dessen Currency-Information beim CP-Gateway gefehlt hat und den der Service als `USD` annimmt. Caller koennen das auswerten, um Multi-Currency-Verteilungen kritisch zu pruefen.

### 8.2 Aggregates (implementiert in v0.10.0)

Aggregations-Layer fuer haeufige Reports - PSM ruft hier gegen `/aggregates`, statt selbst Trade-Listen aufzusummieren.

```
Authorization: Bearer <token (portfolio:read)>
```

`metric` ist ein Whitelist-Wert. In v0.10.0 unterstuetzt:

| Metrik | Bedeutung |
|---|---|


## 9. Events Stream (SSE)

### 9.1 Endpunkt

```
GET /v1/events/stream?types=<csv>
Authorization: Bearer <token (events:read)>
Accept: text/event-stream
```

| Query | Optional? | Beschreibung |
|---|---|---|
| `types` | ja | Komma-separierte Filterliste. Erlaubt: `execution`, `position`, `status`. Default = alle drei. Unbekannte Werte -> `400 Bad Request`. |

| Header | Optional? | Beschreibung |
|---|---|---|
| `Last-Event-ID` | ja | Letzte beim Client gesehene `id`. Server sendet zunaechst gepufferte Events mit `event_id > Last-Event-ID` und schaltet dann auf den Live-Stream um. |

### 9.2 Event-Typen

Single Source of Truth fuer das Schema: `src/broker_gateway/streams/events.py`. Felder sind additiv - Consumer duerfen unbekannte Felder ignorieren.

`event: execution` (Order-Ausfuehrung, Fill oder Partial-Fill):

```
id: 0
event: execution
data: {"order_id":"ord_abc","account_id":"U25235077","conid":265598,"symbol":"AAPL","side":"BUY","filled_quantity":"0.5","avg_fill_price":"150.50","status":"PartiallyFilled","occurred_at":"2026-04-25T11:30:14.481Z"}
```

`event: position` (Positionsaenderung nach Ausfuehrung):

```
id: 1
event: position
data: {"account_id":"U25235077","conid":265598,"symbol":"AAPL","new_quantity":"11.0","change":"+0.5","occurred_at":"2026-04-25T11:30:14.500Z"}
```

`event: status` (Order-Status-Wechsel ohne Fill):

```
id: 2
event: status
data: {"order_id":"ord_def","account_id":"U25235077","old_status":"Submitted","new_status":"Cancelled","reason":null,"occurred_at":"2026-04-25T11:30:15.001Z"}
```

`id` ist eine vom Server vergebene, **monoton steigende** Event-ID (Single Source of Truth: `EventBus._next_event_id`).

### 9.3 EventBus (Fan-Out)

- Genau **eine** EventBus-Instanz pro App-Lifespan.
- Jeder verbundene HTTP-Consumer bekommt jeden Event seines Filters; der Bus fan'ed in alle Queues gleichzeitig.
- Ringpuffer (Default 200 Events) erlaubt Reconnect via `Last-Event-ID`. Wenn der Reconnect zu spaet kommt, fehlen Events - Consumer sollte in dem Fall einen `/v1/orders/{id}` (Status) und `/v1/portfolio/{accountId}/positions` (Positionen) als Cold-Start ergaenzen.

### 9.4 Source-Implementierung (Status v0.11.0)

In v0.11.0 enthaelt `broker-gateway` noch keinen aktiven CP-Gateway-WebSocket-Adapter. Die Events-Quelle ist eine Schnittstelle (`EventSource`), die Tests und ein spaeterer Adapter implementieren. Solange noch keine Source registriert ist, liefert der Bus nur Events, die andere Komponenten direkt einspeisen (z.B. interne Test-Hooks). Das CP-Gateway-WebSocket-Backend (`/v1/api/ws`) wird in einer Folgekarte angeschlossen, ohne dass sich das Wireformat aendert.

**Hinweis TWS-Backend (ab v1.34.0):** Im `BG_BACKEND=tws`-Pfad ist der Events-Stream noch nicht angeschlossen — `ib_async` liefert Order-/Trade-/Position-Updates über Event-Callbacks (`updateEvent`, `execDetailsEvent`, `orderStatusEvent`), aber die Bridge in den `EventBus` ist Teil der Single-Owner-Coordination-Karte (Folgekarte 4). Solange läuft der Events-Stream nur unter `BG_BACKEND=cp` produktiv.

### 9.5 Limits + Fehlercodes

| Status | Bedingung |
|---|---|
| `400 Bad Request` | `types`-Filter enthaelt unbekannte Werte |
| `401 Unauthorized` | Bearer fehlt oder ungueltig |
| `403 Forbidden` | Token besitzt nicht `events:read` |
| `503 Service Unavailable` mit `Retry-After: 30` | `auth_status in {auth_lost, cp_down}` (siehe Section 3.2) |

## 11. Internals (nicht öffentlich)

Nur dokumentiert für Service-Entwickler, nicht für Consumer:

- **Subscription-Refcount-Map:** `{conid → {fields-bitmask → ref_count}}`
- **Order-Cache:** `{order_id → order_state}` mit TTL 24 h für Idempotency-Antworten
- **Auth-Session-Heartbeat:** Hintergrund-Job hält die IBKR-Session lebendig. CP-Backend: alle 60 s `POST /tickle` an CP-Gateway. TWS-Backend (ab v1.34.0): alle 60 s `ib.isConnected()` + `ib.client.isReady()` über die `ib_async`-Socket-Verbindung. Konfigurierbar via `BG_CP_TICKLE_INTERVAL_S` bzw. `BG_TWS_HEARTBEAT_SEC`.
- **Field-Mapping-Tabelle:** normalisierte Quote-Field-Namen ↔ IBKR-Field-IDs (z.B. `last` ↔ `31`, `bid` ↔ `84`)
- **Reconnect-Logic:** CP-Backend bei Session-Drop: 3 Versuche `reauthenticate`, dann `503` mit `Retry-After: 30` für Consumer und `auth_status=auth_lost` im Health-Endpoint. TWS-Backend (ab v1.34.0): Connect-Retry bis `BG_TWS_MAX_CONNECT_FAILURES` (Default `3`), dann `auth_status=tws_down`; kein expliziter Reauth — IB Gateway + IBC machen Daily-Restart und Saturday-Reset selbständig.

### 11.1 Rate-Limit-Throttle (Token-Bucket pro Endpoint-Klasse)

Alle CP-Gateway-Calls passieren `ThrottleManager` (Single Source of Truth: `src/broker_gateway/throttle/manager.py`). Pro Klasse existiert genau ein Token-Bucket. Der ThrottleManager bleibt CP-spezifisch — die TWS-API hat ein eigenes Pacing-Modell auf TCP-Frame-Ebene, das `ib_async` selbst durchsetzt; ein Refactor des Service-Layers mit echten TWS-Bucket-Klassen ist Teil der Single-Owner-Coordination-Karte (Folgekarte 4).

| Klasse | Default rps | Default Burst | Pfade |
|---|---|---|---|
| `auth_lifecycle` | 5 | 10 | `/tickle`, `/reauthenticate`, `/iserver/auth/status` |
| `instruments` | 5 | 10 | `/iserver/secdef/*` |
| `quotes_snapshot` | 10 | 20 | `/iserver/marketdata/snapshot` |
| `quotes_stream` | 10 | 20 | `/iserver/marketdata/{conid}/unsubscribe` (Poll-Loop pro conid) |
| `portfolio` | 5 | 10 | `/iserver/account/{acct}/{portfolio,positions,ledger}` |
| `orders` | 5 | 10 | `/iserver/account/{acct}/orders`, `/iserver/account/orders/{id}`, `/iserver/account/{acct}/order/{id}`, `/iserver/reply/{id}` |
| `trades` | 2 | 5 | `/iserver/account/trades` |
| `events` | 5 | 10 | `/v1/api/ws...` (Folgekarte) |

Jede Rate ist via ENV einstellbar: `BG_THROTTLE_<CLASS>_RPS` und `BG_THROTTLE_<CLASS>_BURST` (z.B. `BG_THROTTLE_QUOTES_SNAPSHOT_RPS=20`).

**Pacing-Violation-Backoff:** liefert das CP-Gateway HTTP 429, ruft der Client `bucket.register_pacing_violation()`. Der Bucket setzt einen `extra_wait_s` ein (Start 0.5 s, verdoppelt mit ±20 % Jitter, gedeckelt auf 30 s), den nachfolgende Acquire-Calls zusaetzlich abwarten. Nach 5 erfolgreichen Calls in Folge wird der Backoff zurueckgesetzt.

**Constraint Tickle-Bucket:** der `auth_lifecycle`-Bucket ist von den anderen entkoppelt - eine Pacing-Violation auf `quotes_snapshot` blockiert nicht das Tickle-Job-Heartbeat. Damit bleibt die Session auch unter Last lebendig.

### 14.1 TWS-Backend-Refactor (v1.32–v1.34, Mai 2026)

Karten 368ccdfe (Spike), 8b1781d3 (Container-Slot), 441b53db
(TWSClient-Adapter) und 33cb35b1 (TWSLifecycle + `BG_BACKEND`-Switch)
führen die interne IBKR-Datenquelle parallel zum bestehenden
cpgateway-Pfad auf die TWS-Socket-API über `ib_async` um. Diese Karte
(45b03110) zieht die Doku nach.

**Konsumenten-Vertrag (`/v1`-API):** unverändert. Kein neuer Endpunkt,
keine umbenannten Felder. Das Schema von `/v1/internal/health` wurde
additiv erweitert (`auth_status_consumer`-Feld, ab v1.34.0) — Konsumenten,
die nur das frühere Schema lesen, sind nicht betroffen.

**Was sich intern geändert hat:**

- **Auth-Lifecycle (Section 3.2):** zweiter Pfad `TWSLifecycle` parallel
  zu `AuthLifecycle`. Heartbeat statt Tickle, kein Reauth (IB Gateway +
  IBC machen Daily-Restart und Sat-Reset selbst). Neue Status-Werte
  `session_lost` und `tws_down` im `AuthStatus`-Enum (Single Source of
  Truth: `broker_gateway.auth_status`).
- **503-Guard:** `require_session_ok` ruft jetzt `is_session_unavailable`
  aus `auth_status.py` und reagiert backend-unabhängig (auch auf
  `tws_down`/`session_lost`).
- **ENV-Tabelle (Section 3.2):** `BG_BACKEND`, `BG_TWS_HEARTBEAT_SEC`,
  `BG_TWS_HOST`, `BG_TWS_PORT` ergänzt.
- **Internals (Section 11):** Heartbeat-/Reconnect-Bullets backend-aware
  formuliert.
- **Throttle (Section 11.1):** Hinweis ergänzt, dass der CP-spezifische
  ThrottleManager im TWS-Pfad nicht greift; ein TWS-Bucket-Layer ist
  Teil der Single-Owner-Coordination-Karte (Folgekarte 4).
- **Events (Section 9.4):** Hinweis, dass der EventBus-Adapter für die
  TWS-Event-Callbacks ebenfalls in Folgekarte 4 entsteht.

**Service-Schicht-Limitation unter `BG_BACKEND=tws`:** `PortfolioService`,
`OrdersService`, `QuotesService` rufen weiterhin `CPGatewayClient` auf,
nicht `TWSClient`. Funktional sind im TWS-Pfad heute nur `/v1/health`,
`/v1/internal/health` und `/v1/internal/tws-health` (TWS-Diagnose-Endpunkt
aus Karte 441b53db). Business-Endpunkte werfen ohne laufenden cpgateway-
Container `ConnectionError`. Der TWS-Adapter ist also Backend-Slot, nicht
End-to-End-Cutover — der erfolgt in Folgekarte 6.

**Drift gegen TWS-Backend:** noch keine systematische Live-Smoke-Runde
(nicht Teil dieser Karte). Der bestehende Drift-Bericht oben gilt für
den CP-Pfad gegen DUP799747; die TWS-Fixtures in `tests/test_tws_*.py`
(Karten 441b53db + 33cb35b1) decken Adapter und Lifecycle Mock-seitig
ab. Live-TWS-Drift wird mit der Single-Owner-Coordination-Karte (4)
oder dem Hard-Cutover (Karte 6) als Acceptance-Gate eingezogen.

### 14.3 Spec-Drift `POST /v1/orders/whatif` behoben (Karte `fe164f56`, v2.3.0)

Section 7.4 (What-If/Preview) war bis v2.2.x in der Spec geführt, aber
nicht implementiert — ein Router-Scan über `src/broker_gateway/api/`
fand keinen `/whatif`-Handler. Karte `fe164f56` (Variante A) hat den
Endpoint additiv implementiert, damit Spec == Code gilt:

- **Implementierung:** `POST /v1/orders/whatif` via TWS-Backend
  (`ib_async.whatIfOrder` → `OrderState`), Response-Modell
  `WhatIfPreview` (SSOT in `order_models.py`). Scope `orders:read`
  **oder** `orders:write` (`require_any_scope`, analog `GET
  /v1/orders/{id}`). Kein `Idempotency-Key`, da reine Vorschau.
- **Bewusste Abweichung vom alten Spec-Beispiel:** Die Margin-Felder
  spiegeln jetzt `ib_async.OrderState` (equityWithLoan/initMargin/
  maintMargin) statt der vorformatierten cp-Strings; alle Geldfelder
  sind optional und werden nie geschätzt, wenn das Backend sie nicht
  liefert. Section 7.4 wurde entsprechend aktualisiert.
- **cp-legacy:** liefert `503 whatif_not_supported_on_cp` — das
  CP-Gateway-Object (`amount/equity/initial/maintenance/warns`) mappt
  nicht verlustfrei auf das maschinenlesbare Schema, und cp ist seit
  v2.0.0 nur noch Roll-Back-Profil.

**Read-Only-Befund aus dem Paper-Smoke (v2.3.1):** Der erste Live-Smoke
gegen DUP799747 (read_only=yes) deckte auf, dass IBKR `whatIfOrder` im
Read-Only-API-Modus mit `Warning 321` ablehnt — **ohne** OrderState,
sodass `whatIfOrderAsync` endlos hängt. Die ursprüngliche Annahme
(v2.3.0), whatif sei "semantisch read-only" und im read-only-Stack
nutzbar, war falsch. v2.3.1 korrigiert das: ein proaktiver
`503 whatif_requires_write_session` im read-only-Modus (kein Hang) plus
ein 15s-`asyncio.wait_for`-Timeout (`504 tws_whatif_timeout`) als
Absicherung für Write-Sessions. whatif ist damit wie `POST /v1/orders`
an eine nicht-read-only Session gebunden. Konsequenz: auf den heutigen
cma-pi-1-Stacks (beide read_only) liefert der Endpoint den
dokumentierten 503; eine echte Vorschau ist erst auf einem Stack mit
`READ_ONLY_API=no` möglich.

Damit ist der Router-Scan deckungsgleich mit der Endpoint-Liste in
dieser Spec.
